The stack — resolve low, escalate up, watch it all

Context and cost rise as you climb. Cheap domain-scoped roles absorb the routine; ambiguity escalates up to the expensive full-context architect; and the overseer sits over the whole pipeline.

Overseeralways-on
Watches the whole pipeline: no never-ending loops, each deliverable cost-consistent with the last; monitors the service, can stop/restart it. ("The you part.")
Architectambiguity / ratified change
Full context → expensive. Fires on two triggers only: an ambiguity a director escalates, or a precedent-level business change that needs ratifying directly. Writes the ruling into the spec of record and queues operational tickets to the overseer.
Traffic-copevery task
Owns the queue; routes work; escalates ambiguity up rather than guessing.
Directorevery review
Domain-scoped → cheap. Scores candidates against an authored rubric and catches gaps. Absorbs the bulk of decisions so architect calls stay rare.
Research · Dev-executor · Verifierexecution
Author the spec + rubric · propose a candidate into a separate slot · gate the loop on a green re-test.

Task 1 — the clean loop (no escalation needed)

healed detect 2✗→ research spec+rubric→ dispatch→ fix candidate→ director 9/10→ apply→ verify ✓ 2 → 0 fail

A pricing bug (wrong discount threshold + tax base). Fixed and vetted in one pass — the director approved a correct candidate, no ambiguity to raise. Most work looks like this — nothing to raise, so the escalation layers never wake.

Task 3 — a live service goes stale, and the overseer restarts it

A real pricing service is running on 127.0.0.1:8899. It imported the pricing module at startup and holds it in memory — so a change on disk does not reach it. That makes drift a real, observable condition, and the only fix is a restart.

overseerservice_watch
Live service up (pid 52688). Baseline captured: tax 10%, /price?sub=100 → 88.00.
architectticketTKT-001
A business rule changes: sales tax 10% → 8%. Ratified into the spec — and the architect flags the operational consequence itself: the running process holds the old rate in memory and will keep serving it no matter what the code says. Severity: non-catastrophic. Service action routed to the overseer.
traffic_copdispatch
Splits the ticket: code change → dev-executor; service action → overseer.
dev_executorapplied
Ratified constant change applied: TAX_RATE 0.10 → 0.08, plus the four dependent test expectations.
verifierverify_passDISK 4/4
All four cases green on disk at the new rate (43.20 / 86.40 / 172.80 / 81.00). By every normal signal, the job is done.
overseerdrift_detectedNON-CATASTROPHIC
But the service is quietly wrong. Probing the live process: tax 0.10, /price → 88.00, while disk says 0.08 → 86.40. The process is up, the health check is green, the suite is passing — and customers are being charged the superseded rate. Only a role watching the running service catches this.
overseerlog_triage
Reads the raw service log and reduces it to a signature ({service_start:1, health:2, price:3}, all responses carrying the stale rate, 0 errors) rather than forwarding the raw log up the ladder — the cheap role absorbs the volume so the expensive architect's context doesn't have to.
overseerservice_stopped
Stops the live process (pid 52688 terminated, confirmed down) to clear the stale in-memory module.
overseerservice_restartedNEW PID 25444
Brings the service back up. The new process re-imports the module and now serves the ratified rate. A different PID is the proof it is genuinely a new process, not a reload.
verifierverify_passLIVE ✓
Live service now reconciled with disk: tax 0.08, /price → 86.40, member → 81.00. Verified against the running process, not the test suite.
overseercost_consistencyWITHIN BAND
Task 3 ran 11 steps: one architect ticket, zero loops, one service intervention. Accounted for and within band.
What the top of the ladder is for Routine work resolves at the cheap bottom rungs; the costly top only wakes for the exceptions. Across three tasks the architect ran twice — once to rule on an unratified rule, once to ratify a business change and flag its operational fallout — and the overseer intervened once, on the one failure no test could have caught. Task 1 needed neither. That distribution is the design: if the architect ran on every question it would be unaffordable, and without an overseer watching the running service, a green test suite would have signed off on a service charging the wrong tax.
Limitations "Self-healing" names the closed loop, not an autonomous goal-seeker. The apply and service-recovery steps run without a human; in Tasks 1 and 2, detection and the brief are not self-originating — they come from a test signal, a probe, or a ratified ticket. In Task 3 the overseer's drift detection is self-originated, catching a stale-service failure the passing test suite could not. Every candidate still passes a review gate before it touches a live file. And this page is a static replay of a recorded run: it proves what happened and when, and is not itself a live system.
The same stack, at production scale This shape authored a full production system's content and code through a brief→generate→extract→review→ledger cycle, across ≈55 dev briefs in one subdirectory (fix and feature work combined), with the director issuing real REVISE verdicts (one constraint recovered across an APPROVE(9)→REVISE(6)×2→APPROVE(8)×3 arc) and a dual-judge audit on two model families. That system was later migrated to a key-free two-tier substrate; the fix-cycle evidence above predates the migration, and its cost figures are modeled token cost, not billed spend. The toy on this page runs at $0 for a different reason — it executes in-session on quota-based billing.
